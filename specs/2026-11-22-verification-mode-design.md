# Verification mode: design

Status: approved on 2026-11-22 as the last item of the 0.8.0 plan. On 2026-11-22 the user chose approach 1 (a generated rates file beside the bank), chose to ship the newest models' claims marked, without a new collection, and chose to change exit codes only when `--claim` is passed.

## Intent

The person running `lping` usually knows which model an endpoint claims to serve: they pass it as `--model`, which the interactive prompt already calls the "Claimed model identifier". The main use case is an untrusted relay or reseller that might quietly serve a different model. Asking "is this run consistent with the claimed model?" is a better-posed question than naming the model from scratch. It targets the failure the probe has real power against, a silent swap.

Verification answers that question for one claim. It also says, from offline measurements, how much the answer is worth for that particular claim. A claim of `claude-sonnet-5.5` is rarely accepted for another model's runs. A claim of `gpt-6.2-sol` is accepted for most runs of models the bank doesn't know. A bare "consistent" would hide that difference, so the verdict always carries the measured rates for its claim.

## Goals

- Every probe that names an enrolled model gets a claim verdict, with the claim's measured acceptance rates whenever they apply.
- Rates are regenerated with the evaluation report from stored runs, with no provider requests, and a test fails when they no longer match the bundled bank.
- Rates are honest about their basis: every rate carries its run counts and a 95% range, and rates from tuning runs say so.

## Non-goals

- No new collection. The 8 models without independent runs ship with tuning-run figures, marked.
- No new decision rule. A claim is accepted exactly when the claimed model is among the `candidates` that 0.8.0 already computes.
- No change to identification: statuses, `model`, `candidates`, scores and banks stay as they are.
- No rates for the pooled bank in 0.8.0. Pooled probes get a verdict, but no rates.

## Anti-goals

Any of these makes the feature a failure, even if it works:

- A verdict shown without its claim's rates when they exist, or a word like "verified".
- A probability that the endpoint runs the claimed model. The rates describe this probe's behavior on stored runs; they are not that probability.
- Rates quoted for a bank, transport or probe they were not measured on.
- Tuning-run and independent figures mixed in one number without saying so.
- Wording that suggests models whose runs pass as a claim are related, derived or trained from one another. They produce similar outputs; nothing more is claimed.

## Constraints

- Node ≥ 22, TypeScript ESM, no new dependencies.
- `src/core`, `src/math` and `src/probes` import no `node:` modules. The new runtime code keeps that.
- The rates file is generated by `npm run bank:evaluate`, which needs the git-ignored maintainer corpora. CI and users only read the committed file.
- The repository is public under a pseudonymous identity: no local paths, usernames or scratchpad paths in generated files, docs or commits.
- In the maintainer's shell, `npm` is a Socket wrapper. Use `./node_modules/.bin/vitest run`, `./node_modules/.bin/tsc --noEmit`, `npm run build` and `node scripts/...`.

## Approaches

1. **A generated rates file beside the bank (chosen).** `npm run bank:evaluate` writes `src/data/claim_rates.json` next to the report. The library bundles it like the bank and attaches its figures only to probes scored with the bundled default bank. The report renders the same table, and its test pins the file to the bank.
2. **Rates stored in each bank entry.** Rejected. They would travel with custom banks, but the report records the bank's SHA-256. Writing evaluation results into the bank would change the hash the report was made from, unless the hash skipped that field. It would also put measured outcomes into the reference data the engine scores against.
3. **A verdict with a pointer to the report.** Dropped: it is the bare "consistent" this design exists to avoid.

## The claim

- **Source:**
  - `EngineOptions.claim?: string` carries the claimed model name as given, such as `openai/gpt-6.2-sol`. An empty string counts as no claim.
  - The CLI passes `--claim <model>` when given, otherwise `--model`, in API and driver mode.
  - `--claim` exists for relays that serve a model under their own alias.
- **Matching:** the claim names an enrolled model if its last `/` segment equals a bank id, ignoring letter case. This is the rule item 4 uses for collection settings, and both use one shared helper. Ids that differ only by case resolve in bank order, as today.
- **Collection settings:** the CLI applies a model's recorded settings for the claimed model, so `--claim` takes precedence over `--model` there too. Without `--claim`, nothing changes.

## Verdicts

`ProbeResult.claim` is present exactly when a claim was given. Its `verdict` is one of:

| Verdict | When |
| --- | --- |
| `CONSISTENT` | The claim names an enrolled model, and that model is in `candidates`. |
| `INCONSISTENT` | The claim names an enrolled model, `candidates` was computed, and the model is not in it. This includes an empty list, so `UNKNOWN_MODEL` results land here, as does an `IDENTIFIED` result naming another model. |
| `NOT_ENROLLED` | The bank in use enrolls no model the claim names. The probe cannot check the claim. |
| `NOT_CHECKED` | The claim names an enrolled model, but the probe computed no `candidates`, or the model is enrolled without calibration (`status: 'uncalibrated'`), so it can never be a candidate. No-candidates cases include `UNCALIBRATED` (among them a CLI driver probe with the bundled API bank), a reply too short to classify, and a bank with a single model. |

Cross-transport comparisons and pooled probes compute `candidates`, so they get `CONSISTENT` or `INCONSISTENT`, but no rates.

## What the rates measure

For each enrolled model of the default bank, as a claim, the generator scores stored 512-integer runs with the production engine (`earlyStopping: false`, as the report does). It counts how often the claim is accepted, meaning the claimed model is in `candidates`, in four populations:

| Population | Runs | Scored with |
| --- | --- | --- |
| `own` | The claimed model's independent runs: those from corpora its bank entry was not enrolled from. If it has none, its 5 tuning runs (the `validation` runs of its enrollment corpus), marked `source: "tuning"`. The two kinds are never combined. | The full bank |
| `enrolled` | Every other enrolled model's independent runs and tuning runs. | The full bank |
| `removed` | The same runs as `enrolled`. | The bank without that run's own model, as the report's "tested model removed" section does |
| `unenrolled` | All runs, both training and validation, of models the bank does not enroll. | The full bank |

**Why tuning runs may stand in for other models but are flagged for the claim's own:**
- A model's integer distribution is fitted on its 10 training runs only. Its tuning runs set its distance envelope, at the largest tuning distance × 1.1.
- For another model's claim, those tuning runs are out of sample: neither that claim's reference nor the run's own distribution was fitted on them.
- For the model's own claim, its envelope accepts them by construction, so the own figure is optimistic.
- Training runs are never used for enrolled models: the run's own reference was fitted on them, which pushes other claims further behind and would understate impostor acceptance.

**Derived figures**, computed by one shared function so the report and the runtime agree:
- `outside` = `removed` + `unenrolled`. The CLI shows it as "models outside the bank".
- Rates are weighted by runs: accepted runs ÷ runs.
- `mostAccepted`: other models whose runs, in the `enrolled` or `unenrolled` population, pass as the claim in at least half of their runs. Sorted by rate, then by runs, then by id. `removed` is a simulation of the same models, so it feeds only `outside`.
- **Range:** each rate has a 95% Wilson score interval, computed from its counts, with lower and upper bounds as fractions. For 5 of 5 that is about 0.57–1.00.

These definitions change the figures you saw on 2026-11-21:
- The own column no longer mixes independent and tuning runs.
- "Outside the bank" now also counts enrolled models with their reference removed, not only the four retired models.

## `src/data/claim_rates.json`

Version 1. The generated file is roughly 18 claims × about 40 rows.

```json
{
  "schemaVersion": 1,
  "bank": { "file": "src/data/default_bank.json", "sha256": "49769c39d5ce…" },
  "corpora": ["0a49c2ace8e2…", "163709a6a446…"],
  "rule": "claimed model in candidates",
  "claims": {
    "gpt-6.2-sol": {
      "own": { "source": "tuning", "accepted": 5, "runs": 5 },
      "runs": [
        { "model": "gpt-6.1-sol", "population": "enrolled", "accepted": 58, "runs": 60 },
        { "model": "gpt-6.1-sol", "population": "removed", "accepted": 60, "runs": 60 },
        { "model": "gpt-5.6-sol", "population": "unenrolled", "accepted": 70, "runs": 70 }
      ]
    }
  }
}
```

- `bank.sha256` is the SHA-256 of the bank file's text, the same value `docs/evaluation.json` records.
- `corpora` lists the full SHA-256 of every corpus read, sorted. The example shortens them.
- `claims` is keyed by bank id, in bank order, with one entry per enrolled model.
- `runs` holds one row per other model and population with at least one run. Rows are sorted by population (`enrolled`, `removed`, `unenrolled`), then by model id.
- All counts are nonnegative integers, with `accepted ≤ runs`.
- The figures in the example are illustrative.
- The file holds raw counts only. Rates, ranges, `outside` and `mostAccepted` are derived at read time.

The library validates the file when it loads it, as it validates banks. A malformed file is a packaging error and throws `INVALID_BANK`.

## `ProbeResult.claim`

```ts
export type ClaimVerdict = 'CONSISTENT' | 'INCONSISTENT' | 'NOT_ENROLLED' | 'NOT_CHECKED';

export interface ClaimCheck {
  /** The claimed model name as given, e.g. 'openai/gpt-6.2-sol'. */
  requested: string;
  /** The enrolled model the claim names; null for NOT_ENROLLED. */
  model: string | null;
  verdict: ClaimVerdict;
  /** One sentence explaining the verdict, e.g. which model the probe named instead. */
  reason: string;
  /**
   * How often this probe accepts the claim on stored runs, measured offline. Null when no rates were
   * measured for this bank and probe (custom or pooled banks, cross-transport comparisons) and for
   * NOT_ENROLLED. Not a probability that the endpoint serves the claimed model.
   */
  rates: ClaimRates | null;
}

export interface AcceptanceRate {
  accepted: number;
  runs: number;
  /** Bounds of the 95% Wilson score interval of accepted / runs. */
  low: number;
  high: number;
}

export interface ClaimRates {
  /** The claimed model's own runs; 'tuning' runs set its envelope, so that figure is optimistic. */
  own: AcceptanceRate & { source: 'independent' | 'tuning' };
  /** Runs of other enrolled models, scored with the full bank. */
  enrolled: AcceptanceRate;
  /** Runs of models outside the bank: unenrolled models, and enrolled models scored without their own reference. */
  outside: AcceptanceRate;
  /** Other models whose runs pass as this claim in at least half of their runs, most often first. */
  mostAccepted: { model: string; enrolled: boolean; accepted: number; runs: number }[];
}
```

`rates` is attached only when all of these hold:
- the verdict is `CONSISTENT` or `INCONSISTENT`;
- `fingerprint()` was called without `bank`, so it scored with the bundled default bank it loaded itself;
- the probe is not a cross-transport comparison.

A bank passed in gets no rates, even an object `defaultBank()` returned or an identical file copy, because the caller could have changed it. This is my call: tracking `defaultBank()` objects would attach rates to a modified copy (`scripts/package-smoke.mjs` already modifies one), and hashing the 9.5 MB bank on every probe is too slow. The CLI already passes no bank when it uses the bundled one. The report test pins the bundled file to `bank.sha256`. The rates still apply to `INCONSISTENT`, because `own` tells how often the claimed model's own runs fail.

## CLI output

The claim block goes after the integer, token and early-stop lines, and before the notes. A `NOT_CHECKED` verdict prints nothing, because the status line already explains why. JSON output carries `claim` as above. The figures below are illustrative.

```
Claim gpt-6.2-sol: consistent
  Accepted for 5 of 5 of its own runs (tuning runs; likely 57–100%).
  Also accepted for 43% of other enrolled models' runs (233 of 545) and 79% of runs from models outside the bank (612 of 770).
  Most often accepted for: gpt-5.6-sol 70/70, gpt-6.1-sol 58/60, gpt-6-astra 52/60 (+2 more).
```

```
Claim claude-sonnet-5: inconsistent
  claude-sonnet-5 is not among the candidates; no enrolled model fits this run.
  Its own runs are accepted only 15 of 40 times (38%; likely 24–53%), so this is weak evidence against the claim.
```

```
Claim gpt-7: not checked; the bank enrolls no model named gpt-7.
```

Without rates, the second and third lines become: `No acceptance rates were measured for this bank and probe.` The last clause of the `INCONSISTENT` example appears only when the own rate's upper bound is below 0.9. That threshold is the builder's call, if a better one turns up.

## Exit codes

The user's decision, 2026-11-22: exit codes change only when `--claim` is passed.

| Probe | Exit code |
| --- | --- |
| With `--claim` | `0` for `CONSISTENT`, `3` for `INCONSISTENT`, `2` for `NOT_CHECKED` or `NOT_ENROLLED` |
| Without `--claim` | As today: `0` for `IDENTIFIED`, `2` for the other statuses, even when `--model` names an enrolled model |

- Errors still exit `1`, and interruptions `130`, with or without `--claim`.
- Without `--claim`, the claim taken from `--model` appears only in the readable output and the JSON. Existing scripts see no change: a genuine `claude-sonnet-5` endpoint, whose own runs often fail its claim, and parameter drift that ends in `UNKNOWN_MODEL` keep their current codes. No opt-out is needed, because the implicit claim never changes the exit code.
- With `--claim`, a relay that cuts its reply short, or any probe that cannot check the claim, exits `2`, not `0`.
- Exit `0` under `--claim` does not say how strong the claim is: a weak claim such as `gpt-6.2-sol` passes for many other models. Scripts that care read `claim.rates` from the JSON.

`--claim` takes a non-empty value; an empty one is an invalid argument.

## Generation, report and tests

- `scripts/evaluate-banks.mjs` writes `src/data/claim_rates.json` along with `docs/evaluation.json` and `docs/evaluation.md`, and prints one summary line for claims.
- The claim counts come from the same scoring pass as the report's tallies wherever the runs overlap. The new runs are the tuning runs of enrolled models.
- `docs/evaluation.md` gains a "Claims" section rendered from `claim_rates.json`, one row per claim:
  - claimed model;
  - own runs, with source and range;
  - other enrolled models' runs;
  - models outside the bank;
  - most often accepted.

  It also states the populations and the tuning-run caveat. `docs/evaluation.json` keeps its schema; its existing sections and figures do not change.
- `tests/evaluation-report.test.ts` also checks:
  - `claim_rates.json` records the bundled bank's SHA-256;
  - its claims are exactly the bank's ids, in order;
  - the committed Markdown equals the render of both files;
  - it records no local paths.
- Unit tests cover:
  - each verdict;
  - claim matching (prefix, case, no match, `--claim` precedence);
  - when rates are attached, and when they are not (custom bank, a file copy of the bundled bank, pooled, cross-transport);
  - the Wilson bounds and the derived figures on a small fixture;
  - `mostAccepted` ordering;
  - file validation;
  - the CLI block, and exit codes with and without `--claim`.

## Errata

Changes the final review prompted, on 2026-11-22:

- **Matching:** a claim first names the bank model whose whole id equals it, ignoring case, and only then the one whose id is its last `/` segment. Bank ids may contain `/`, and the last-segment rule alone reported such a model as not enrolled. Collection settings share the helper, so they gain the same fix.
- **`NOT_CHECKED` output:** the CLI prints `Claim <name>: not checked; <reason>` when the claimed model is enrolled without calibration, because the status line does not explain that case. When no candidates were computed it still prints nothing.
- **Cross-transport reasons:** the claim reason is built from the relabelled result, so a `HEURISTIC_MATCH` across transports is never called an identification.
